# D-Apo（Dentia）— 歯科医院 架電CRM システム概要

> 外部の第三者（AI含む）に助言を求めるための、システム全体のまとめ。
> 最終更新: 2026-09-22

---

## 1. これは何か

**全国の歯科医院に電話営業（テレアポ）をかけるための、少人数チーム向け業務システム。**

営業担当者がスマホを片手に「電話をかける → 結果を残す → 次に進む」を高速で回すことに全振りしている。PC向けの汎用CRMではなく、**モバイルでの架電作業そのものに最適化**したツール。

### 売っている商材（重要）

架電先には2種類の商材を売り分ける。どちらを提案するかは**相手がホームページを持っているか**で決まる。

| 相手の状態 | 提案する商材 |
| --- | --- |
| ホームページが**ない** | **ホームページ制作** |
| ホームページが**ある** | **クチコミ増援サービス** |

どちらに転んでも売る商材があるため、架電の「外れ」が原理的に存在しないのが営業設計上の特徴。

### 想定ユーザー

社内の営業担当 数名。全員が同じ合言葉でログインし、アプリ内で「自分は誰か」を選ぶ。顧客（歯科医院側）はこのシステムを一切触らない。

## 4. 認証・権限モデル（設計上の割り切りあり）

Supabase Auth は使わず、**チーム共通の「合言葉」1つ**でログインする。

1. `/login` で合言葉を入力 → HMAC署名付きCookie（`d_apo_session`、30日）を発行
2. ログイン後、`members` テーブルから「自分は誰か」を選ぶ（`d_apo_member` Cookie に保持）
3. 以降、架電結果やプレゼンスに自分の名前が記録される

### セキュリティ上の割り切り

- RLS は **anon ロールに SELECT / INSERT / UPDATE を全面開放**している（`supabase/auth-simplify.sql`）
- anon キーはブラウザに露出するため、**キーを知っていればDBに直接アクセスできる**状態
- 社内利用 + 中身が公開オープンデータ中心、という前提での割り切り
- **DELETE ポリシーは意図的に無し**（誤削除の防止）
- → 「機微な個人情報は入れない」運用ルールで担保している

**ここは外部レビューを受けたい論点の1つ。**

## 5. データモデル

### `clinics` — 医院マスタ（本体）

| 列 | 内容 |
| --- | --- |
| `id` | UUID |
| `external_id` | 厚労省データのID。**再取り込みの冪等キー**（unique） |
| `name` / `address` / `prefecture` / `city` | 基本情報 |
| `phone` | 電話番号 |
| `business_hours` | 表示用の診療時間テキスト |
| `hours` | **曜日別の診療時間（jsonb）**。昼休みは区間分割、空配列＝休診 |
| `lat` / `lng` | 座標 |
| `status` | 架電ステータス6種（後述） |
| `assigned_to` | 担当者（members への FK） |
| `next_action_at` | 次回アクション日時（折り返し予定） |
| `latest_memo` | 最新メモ（一覧表示用のキャッシュ） |
| `source` / `phone_source` / `phone_verified` | データの出所と確認状態 |
| `place_id` | Google Place ID（規約上、保存が許容される唯一のPlacesフィールド） |
| `website_url` | ホームページURL |
| `website_status` | `has` / `none` / `unknown` の3状態 |
| `website_source` | `mhlw` / `google` / `call` |
| `website_checked_at` | 確認日時 |

### `call_logs` — 架電履歴（追記のみ、削除しない）

`clinic_id` / `user_id`（members） / `outcome`（6種） / `memo` / `created_at`

### `members` — 担当者

`id` / `name` / `color`（アバター色） / `created_at`

### `phone_candidates` — 電話番号の確認キュー

自動採用できなかった候補を人が承認/却下するためのテーブル。
`place_id` / `name` / `formatted_address` / `phone` / `distance_m` / `name_score` / `confidence` / `status`

### `profiles`

Supabase Auth 時代の名残。現在は実質未使用。

### ステータス6種（`clinics.status` と `call_logs.outcome` で共通）

`not_called`（未架電）/ `no_answer`（不通）/ `unavailable`（担当者不在）/ `heard`（ヒアリング済）/ `appointment`（**アポ獲得＝ゴール**）/ `rejected`（お断り）

## 7. 実装済みの主要機能

### 架電作業まわり
- **ワンタップ発信**（`tel:` リンク）
- **「次に電話する医院」の自動選出** — 未架電を最優先 → 折り返し対象（不通・担当者不在）→ その他。さらに各優先帯の中で**いま診療中（JST基準）の医院を優先**し、昼休み・休診への無駄架電を減らす
- **営業中判定** — `hours` から「営業中／昼休み／営業時間外／休診」をJST基準で判定してバッジ表示
- **スワイプ操作** — カードを左スワイプで「結果入力」、右スワイプで「発信」
- 架電結果＋メモを `call_logs` に蓄積し、一覧用に `latest_memo` を同期

### チーム連携
- **Realtime 同期** — Supabase Realtime で他端末の変更が即時反映（トースト通知つき）
- **プレゼンス** — 誰が今「架電中」「一覧を閲覧中」などを表示

### 絞り込み（全8種）

| 絞り込み | 値 | 複数選択 |
| --- | --- | --- |
| 検索 | 医院名・住所のフリーワード | — |
| ビュー | すべて / 自分の担当 / 要フォロー / 未架電 | ✗ |
| 都道府県 | 47都道府県 | **✅** |
| 市区町村 | テキスト部分一致 | — |
| 架電 | まだかけてない / かけた | ✗ |
| 種別 | 医療法人 / 個人・その他（名称パターンで判定） | ✗ |
| ホームページ | HPあり / HPなし・未確認 | ✗ |
| ステータス | 未架電〜お断りの6種 | **✅** |

**項目どうしは AND、同じ項目内の複数選択は OR。** URLパラメータに反映されるので条件を共有できる。該当件数の表示とCSV出力あり。

## 8. データの出所と、その限界（重要）

### 医院マスタ — 厚労省「医療情報ネット（ナビイ）」オープンデータ

- ZIP/CSV配布。APIキー・課金・保存制限なし
- `external_id` を衝突キーに **upsert** するため、再取り込みしても**架電の進捗・メモ・手入力した電話番号は保持される**

#### カバー率の問題（解決不能と結論済み）

| | 件数 |
| --- | --- |
| 実際の全国 歯科診療所数（厚労省 医療施設調査 令和5年） | **66,818** |
| 医療情報ネットのオープンデータ（＝取り込み元） | **52,985** |
| 差分 | 13,833（約21%が存在しない） |

**元データを全47都道府県ぶん実測したところ、取り込み件数と完全に一致（差ゼロ）。** つまり取りこぼしではなく、**元データ自体が不足している**。

原因は、医療情報ネットが2024年4月に都道府県別システムを全国統合したばかりで、**県ごとに登録の進み具合が違う**こと。カバー率は 沖縄17% / 京都28% ～ 栃木102% / 熊本99% と極端にバラつく。

→ 無料で埋める手段がないため、**現状の79%で運用する判断**。将来のMHLW更新版で自然に増える見込み。

### 電話番号 — ナビイのスクレイピング（Google API 不使用）

オープンデータCSVに電話番号が無いため、ナビイの施設詳細ページから取得している（Playwright、1req/秒、識別可能なUA）。結果 49,691件（93.8%）を取得済み。**Googleには1円も払っていない。**

### ホームページ — オープンデータの「案内用ホームページアドレス」列

26,583件（50.2%）。ただし**空欄＝HPが無い、ではない**。届け出ていないだけで、報告率に地域差が激しい（東京65% / 鳥取18%）。

→ このため `none`（確認済みでなし）と `unknown`（未確認）を**明確に分けている**。「HPお持ちでないですよね？」→「ありますけど」の事故を防ぐため。

→ 未確認分をGoogle Places APIで潰すことは可能だが、**Googleの規約でURLの長期保存が禁止**されている。そのためGoogle由来は「有無」だけ記録しURLは保存しない設計にしてある。なお**架電時に本人に聞けば0円かつ最も正確**なので、そちらを主軸に据えている。

## 10. 既知の制約・弱点

1. **DBが勝手に止まる** — Supabase無料プランのため1週間アクセスが無いと自動停止し、アプリが無言で壊れる（実際に発生済み）
2. **エラーを握りつぶす実装が多い** — DB接続失敗時に「メンバー0人」「登録しても無反応」となり原因が分からなかった。エラーの可視化が未実装
3. **anonキー全開放のRLS**（前述）
4. **電話番号が無い3,294件は架電できない**
5. **院長名（管理者名）が無い** — 「〇〇先生いらっしゃいますか」と言えない。地方厚生局の「保険医療機関の指定状況」に医療機関コード・名称・所在地・電話番号・開設者名・**管理者名（院長）**が揃っているため取り込みを検討中。ただし共通IDが無く、名称＋住所のあいまい一致が必要で工数が読めない
6. **アポ獲得後の導線が無い** — ゴールがアポなのに、アポの一覧・日時管理・リマインドが存在しない
7. **担当者への一括割り当てが無い** — 5万件を数名に配る手段がUIに無い
8. **再勧誘防止の仕組みが無い** — 「お断り」はステータスとして残るだけで、再架電をハード的に止める仕組みは無い

## 11. 助言をもらいたい論点

- この規模（5万件 × 数名）の架電オペレーションで、**まず作るべき機能の優先順位**
- 「お断り」先への**再勧誘防止**をどう実装すべきか（日本の特定商取引法における再勧誘禁止への対応含む）
- **アポ獲得後のワークフロー**をこのシステムに含めるべきか、別ツール（カレンダー等）に逃がすべきか
- 5万件を数名で回すための**リスト配分・進捗管理**の設計
- anonキー全開放のRLSは、社内利用前提ならどこまで許容できるか
- 架電の成果を上げるために、**通話中に画面へ出すべき情報**は何か
